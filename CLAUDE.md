## Project context

This is a court-booking platform (tennis, padel, pickleball, squash, possibly mini-football and other sports) built in Spring Boot as a **personal learning project** to prepare for Java developer interviews. My day job is maintenance of legacy applications, so I am deliberately using this project to learn modern Spring Boot, JPA/Hibernate, Spring Security, caching (Redis), payments, testing, and later microservices.

Planned evolution:
1. **Modular monolith** — one deployable REST API, packaged by feature (domain module), with clean boundaries between modules.
2. **Production hardening** — tests, migrations, observability, containerization, CI.
3. **Microservices** — extract modules into services step by step (strangler fig approach), dealing with data ownership, messaging, sagas, gateway, and tracing.

## Decisions made so far

These were made deliberately, after discussion. Do not "correct" them as if they were mistakes. If you think one of them is wrong, challenge it openly and explain why, and I'll decide.

### Architecture
- **Package by feature (domain), not by layer.** Each top-level package under the main application package is a module. Modules expose a small public API and keep their internals (entities, repositories) package-private where possible. No module reaches into another module's repositories or tables.
- **Code-first API** (hand-written controllers and DTOs) for now. API-first with OpenAPI generation may be introduced later, around the microservices phase.
- **Entities are never exposed directly in the API**; requests and responses use DTOs.

### Database and schema
- **Flyway owns the schema.** Hibernate only validates it (`ddl-auto=validate`); it never creates or changes tables.
- **One migration per logical change.** Applied migrations are never edited (except by wiping the local database during early development).
- **Primary keys:** UUIDv7, generated by the database (`uuidv7()`), for main tables (`venue`, `court`). Integer identity columns for small reference tables (`sport`, `locality`).
- **Enum-like values:** stored as `TEXT` with a named `CHECK` constraint (not PostgreSQL enum types), mapped to Java enums **by name, never by ordinal**.
- **Soft delete** via a `status` column (`ACTIVE`, `ARCHIVED`) on `venue` and `court`. Archived rows are kept for history (e.g. past bookings).
- **Audit timestamps** (`created_at`, `updated_at`, `TIMESTAMPTZ`) on main tables, maintained by the application. The database defaults are only a safety net for inserts made outside the application. Reference tables and join tables have no audit columns.
- **Text validation in the database:** names are required to be already trimmed and non-empty (`CHECK (x = TRIM(x) AND LENGTH(x) > 0)`).
- **Case-insensitive uniqueness** uses expression indexes with `LOWER(...)` everywhere. Queries must use the same expression to benefit from the index.
- **Naming conventions:** singular table names matching the entity (`sport`, `court`); constraint and index names start with the table name (e.g. `court_fk_venue`, `court_venue_id_idx`).
- **Foreign keys are always indexed** explicitly (PostgreSQL does not do it automatically), unless a composite key already covers the column as its leading column.
- **Hard invariants go in the database; rules with legitimate exceptions go in the application.** Invariants that are too costly to enforce in the database (e.g. "every court supports at least one sport") are enforced in the application: request validation plus the domain model.

### Domain model (first slice)
- **sport:** reference data, unique case-insensitive name.
- **locality:** flat list of the largest Moldovan cities (no administrative hierarchy for now; may be added later if villages are needed). Correct diacritics with comma-below letters (ș, ț).
- **venue:** name, address (free text: street and number), locality (required), status, audit columns. Venue names are **not** unique; venues are distinguished by name plus address.
- **venue_operating_hours:** composite primary key (`venue_id`, `day_of_week`), so one opening interval per day (no split hours). `day_of_week` uses ISO numbering 1–7 (Monday = 1), matching Java's `DayOfWeek`. A missing day means closed. Closing must be after opening, **except that a closing time of 00:00 means midnight (end of day)**; 00:00–00:00 means open 24 hours. This rule must be interpreted in exactly one place in the Java code. Likely mapped as an element collection of the venue (to be decided when mapping).
- **court:** belongs to exactly one venue; name unique per venue (case-insensitive, ignoring archived courts, via a partial index); `indoor` boolean, required, defaults to false (deliberate); status and audit columns.
- **court_sport:** many-to-many link between courts and sports. Deleting a court cascades to its links; deleting a sport still in use is restricted.
- **Availability is never stored**; it is derived from operating hours plus bookings. A booking will reference the court, not the sport.
- **Deliberately deferred:** users, roles, venue admins (security phase), bookings, pricing, slot durations, temporary closures (to be modeled as date ranges), country and time zones (single country for now), court surface.

## How to teach me

- **Hints before answers.** When I ask about a bug or a design problem, start with a guiding question or a small hint. Only get more specific if I ask for more. Use roughly this escalation:
  1. A question that points my attention to the right area.
  2. The name of the concept or mechanism involved, plus where to read about it.
  3. A plain-language explanation of what is wrong and the general shape of a fix.
- **Explain the "why."** When you flag something, explain the underlying principle and the consequence of getting it wrong, so I can recognize the same problem elsewhere.

- **Respect the phase.** Don't push microservices patterns, Kafka, Kubernetes, etc. while I'm in the monolith phase unless I ask — but do flag things that will make later extraction painful (e.g. cross-module table access).

### Documentation sources (in order of preference)

## How to review my code

When I ask for a review (typically "review my changes since the last commit" or "review module X"), look at the diff in the context of the whole codebase, not just the changed lines. Check new code against the decisions listed above as well.

### Review output format

Group findings by severity:

- **🔴 Must fix** — bugs, security holes, data corruption risks, race conditions, broken transactional behavior.
- **🟡 Should fix** — design problems, maintainability issues, missing validation/error handling, missing tests for important behavior, module boundary violations.
- **🔵 Consider** — style, naming, idiomatic Spring usage, minor improvements.
- **✅ Done well** — briefly note what I got right, so I know what to keep doing.

For each finding: state **where** (file and approximate location), **what** the problem is, **why** it matters, and a **hint** toward the fix — no code. End with the one or two most important things to learn from this review.

### Review checklist

Check for (as relevant to the change):

- **Correctness & concurrency** — double-booking races, transaction boundaries and propagation, isolation levels, optimistic/pessimistic locking, database constraints as the last line of defense, time zones and slot boundaries.
- **Security** — authentication vs. authorization, ownership checks (e.g. a venue owner may manage only their own courts), password storage, token handling, endpoint exposure, CORS/CSRF decisions, secrets in code or config, input validation, leaking sensitive data in responses or logs.
- **JPA / data access** — entity mapping matching the schema, N+1 queries, lazy-loading pitfalls, entity design and relationships, equals/hashCode on entities, exposing entities directly in the API, migration hygiene, indexes for common queries.
- **API design** — resource naming, HTTP methods and status codes, consistent error responses, pagination, validation, DTO boundaries, versioning.
- **Caching** — what is cached and why, invalidation strategy, TTLs, stale-data risks, cache key design, caching things that shouldn't be cached.
- **Payments** — idempotency, webhook verification and handling, failure and retry paths, consistency between booking state and payment state.
- **Architecture** — module boundaries, dependency direction, no reaching into another module's repositories or tables, logic in the right layer, readiness for later extraction.
- **Testing** — meaningful unit and integration tests, testing behavior rather than implementation, use of real infrastructure where it matters (Testcontainers), tests that prove database constraints surface correctly, edge cases around time and concurrency.
- **Operability** — configuration and profiles, logging quality, health checks and metrics, graceful error handling, no secrets in committed files.
